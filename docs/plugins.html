Build plugins for DarkPurpleOF's Website

A precise, end-to-end reference for the plugin system: how a plugin package is structured, how it's signed and verified, how it runs inside the app, and every native method exposed to it through window.PluginAPI.

01 How plugins work

A plugin is a signed, self-contained web app: a folder of HTML/CSS/JS plus a small manifest, zipped up and installed on-device. It never runs as native code — it's rendered in a sandboxed WebView and talks to the host app through one bridge object.

At a high level, three things happen in order every time a plugin runs:

  1. The app reads manifest.ini out of filesDir/plugins/<id>/, checks the plugin is enabled, and recomputes its integrity hash to make sure nothing has been tampered with since install.
  2. The app starts (or reuses) a local, per-device HTTPS server bound to 127.0.0.1, and resolves your plugin's entry point to a URL served from that origin — never a raw file:// URL.
  3. A WebView loads that URL and gets a JavaScript object, window.PluginAPI, injected into the page. Every capability your plugin has — storage, dialogs, licensing, dependencies, navigation — goes through that one object.
Nothing you ship is trusted by default
Every file in your package is hashed at install time, and that hash tree is checked again on every load. If anything changes on disk outside the app's own runtime writes, the plugin is flagged corrupt and refuses to load until reinstalled.

The sandbox model

Your plugin's HTML runs inside a WebView pointed at https://127.0.0.1:<port>/plugins/<id>/…, served over a self-signed local TLS certificate generated per device. This gives you a real origin (so relative paths, fetch, service-worker-style caching, and browser storage semantics behave normally) without ever touching the filesystem directly or reaching the network by default.

  • Links to http:// or https:// destinations outside the local server trigger a confirmation dialog and open in the system browser — your plugin's WebView never navigates off-origin silently.
  • Any other URL scheme (deep links, intent://, etc.) is blocked outright inside the WebView.
  • A background "freeze watchdog" pings your page on an interval; if your plugin stops responding to JS for too long, the host shows an error page instead of leaving a dead WebView on screen.

02 Package structure

A plugin is distributed as a single .dpplugin file — a standard ZIP archive under a dedicated extension. The installer unpacks it into filesDir/plugins/<id>/ and layers a few runtime-only files on top after install.

your-plugin.dpplugin
├── manifest.ini // required — see §03
├── manifest-ru.ini // optional per-locale override
├── icon.png // optional, recommended ≤256×256
├── icon-ru.png // optional per-locale icon
├── index.html // default entry point
├── screens/
│   └── settings.html // opened via PluginAPI.openLocal("settings")
├── assets/
│   └── style.css, app.js, …
└── META-INF/ // signing metadata — see §07
     ├── root.sha256
     ├── files.sha256
     ├── signature-v1.txt // optional, informational
     └── signature-v2.txt // optional, enforced
Don't ship a data/ folder
Any entry under data/ is stripped out while the installer reads your zip, and it's excluded from the integrity hash. That path is reserved at runtime for what your plugin writes with PluginAPI.saveFile — never for content you ship.

After install, the app writes several small marker files directly into your plugin's folder. These are never part of your zip and are excluded from integrity/signature checks:

enabled.lock disabled.lock corrupt.lock installationSource.dat development-key-expiry.txt

03 manifest.ini reference

A flat key=value file, one entry per line. Blank lines and lines starting with # are ignored. This is the only file the installer and the running app trust for metadata — the rest of your plugin can look however you like.

KeyDescription
idrequiredUnique plugin identifier. Becomes the folder name under plugins/ and the id used everywhere (dependencies, storage, URLs). Stable for the life of the plugin — changing it is treated as publishing a new plugin.
namerequiredDisplay name shown in the plugin list and the WebView title bar.
authorrequiredThe email address of the developer account that owns this plugin. Compared directly against the signed-in user's email to grant the author a free/dev license, and used to look up the developer's display name and verified badge.
versionrequiredNumeric, dot-separated (e.g. 1.4.2). Compared component-by-component; on updates the new version must not be lower than the installed one.
descriptionoptionalShort description shown in the plugin's details view.
iconoptionalNot a manifest key you set directly — the icon is picked up automatically from icon.png / icon-<lang>.png in the package root.
requiresoptionalComma-separated dependency list: pluginA[1.2],pluginB[*]. required= is accepted as an alias. See §05.
lacksoptionalComma-separated capability flags the plugin explicitly does not use: cloud, accounts, data, turnonable. See §06.
manifest.ini
# DarkPurpleOF's Website plugin manifest
id=weather-widget
name=Weather Widget
author=dev@example.com
version=1.0.0
description=Shows today's forecast on your feed.
requires=geo-helper[1.0]
lacks=cloud,accounts

Localization

The app resolves manifests and icons per-device-locale automatically, falling back to the un-suffixed file:

  • manifest-<lang>.ini is preferred over manifest.ini when the device language matches <lang> (a two-letter code, e.g. ru, es).
  • icon-<lang>.png is preferred over icon.png the same way.
  • You can ship as many locale manifests as you want; each is a complete, independent manifest.ini, not a diff.

Dependencies

Declare other plugins yours needs with requires= (or the alias required=):

manifest.ini
requires=geo-helper[1.0],analytics-core[*]
  • Each entry is id[versionSpec]. The bracket is optional — omitting it is the same as [*].
  • * matches any installed version. A numeric spec like 1.2 requires the installed dependency's version to be at least that, compared component-by-component (missing components count as 0).
  • Before your plugin can be enabled, every dependency must be installed, enabled, and version-satisfying — otherwise the toggle is blocked and the user sees exactly which dependency failed and why (missing, disabled, or outdated).
  • Disabling a plugin that other enabled plugins depend on prompts the user for confirmation first, listing every plugin that would break.
The first bracket also gates the host app version
During install, the installer reads the number inside the first bracket in your requires= line and rejects the install outright if it's greater than the user's current app version. If your first dependency's version happens to read higher than most users' app version, install will fail — keep this in mind when ordering dependencies and picking version numbers.

Capabilities — lacks=

Declare things your plugin deliberately does not do. This is informational metadata the host UI and, in one case, install logic reads — it isn't a permissions grant, only a disclosure.

ValueMeaning
cloudNo cloud/remote sync of any kind.
accountsNo account/authentication integration. Plugins that declare this skip the network round-trip the host otherwise makes to verify author/plugin identity.
dataNever writes anything to its own data directory.
turnonableThe plugin cannot be toggled on/off by the user at all — it's always active. Use this for a core/system plugin only.

Entry point & screens

The host resolves whatever "page" you ask for (starting with index on first load) using this order:

  1. If the requested value is already a full http:// or https:// URL, it's loaded as-is (remote content).
  2. Otherwise, it's treated as a page name inside your plugin's folder. .html is appended if missing, and that file is served if it exists.
  3. If that file doesn't exist, the host falls back to index.html at your plugin's root.
  4. If index.html doesn't exist either, the built-in error page is shown instead of your plugin.

Use PluginAPI.openLocal("settings") from within your running plugin to navigate the same WebView to another page in your package (conventionally kept under screens/).

04 The plugin runtime

Your HTML/JS runs like a normal web page. The one non-standard thing available to you is a single injected object, PluginAPI, which is how your code talks to the host app.

Do not reference window.PluginAPI
Avoid using window.PluginAPI in your plugin code. It can break the API bridge; call methods directly on the injected PluginAPI object instead, for example PluginAPI.getLicenseStatus('onLicense').

The callback pattern

Most asynchronous PluginAPI methods take a callback name — a string naming a function already defined on window — rather than a JS function reference or a Promise. The host calls that named function by evaluating callbackName(arg1, arg2, …) back into your page once the native work finishes.

javascript
// define the callback on window first
window.onLicense = function(jsonString) {
  const status = JSON.parse(jsonString);
  console.log('licensed:', status.licensed);
};

// then invoke the API, passing the callback's name as a string
PluginAPI.getLicenseStatus('onLicense');

If you prefer promises in your own code, it's straightforward to wrap this pattern:

javascript
let _n = 0;
function callAPI(method, ...args) {
  return new Promise(resolve => {
    const name = `_cb${_n++}`;
    window[name] = (...res) => { delete window[name]; resolve(res.length>1?res:res[0]); };
    PluginAPI[method](...args, name);
  });
}

// usage
const license = JSON.parse(await callAPI('getLicenseStatus'));

If a function is called badly and the plugin freezes, a time-out error will appear

Some methods are plain synchronous returns
A handful of read-only methods (e.g. getPluginId(), isOnline(), getManifestValue(key)) return their value directly with no callback — they're marked sync below.

Every method exposed on window.PluginAPI, grouped by what it's for. Parameters marked callback are the string-named-function pattern described above.

Returns the host app's own version name.

Returns how this plugin was installed, e.g. "store" or "external".

getLocaleTag()sync

Returns the device's current BCP-47 locale tag.

Returns whether the device currently has network connectivity.

Recomputes and returns the full signature/integrity report for a plugin (pass null for self) — the same status object described in §08.

Lists every packaged file's relative path inside your plugin's install folder.

Licensing & identity

getLicenseStatus(callback)async

Callback receives { licensed, purchased, isAuthor }. isAuthor is true when the signed-in user's email matches your manifest's author field.

getUserEmail(callback)async

Callback receives the signed-in user's email, or an empty string if signed out.

getUserProfile(callback)async

Callback receives { display_name, profile_picture, banner, profile_picture_frame, is_verified } for the signed-in user.

Opens the host's re-authentication sheet; callback fires with "true" once the user re-authenticates.

readDatabase(field)sync

Reads a single field from the signed-in user's cloud profile document. Rate-limited to 10 calls per rolling 60-second window per plugin session — further calls return null until the window resets.

Dependencies

Returns a JSON array describing every declared dependency's install/version status.

isDependencySatisfied(depId)sync

Returns a boolean for one declared dependency.

getDependencyManifestInfo(depId)sync

Returns the dependency's manifest as JSON — only for ids you've actually declared in requires=.

Returns a loadable local-server URL into a declared dependency's package — e.g. to reuse its assets.

List or Base64-read files from a declared dependency's data directory (not its package files).

Callback receives an array of plugin ids that declare your plugin as a dependency.

Reads every pending message addressed to you, each shaped as { from, message, timestamp }. Pass true to consume them.

Local storage

Every plugin gets a private data directory. Filenames are relative to it — you never see or need the absolute path.

saveFile(filename, base64Data, callback) / readFile(filename, callback)async

Write or read a file in your data directory as Base64. Subfolders in filename are created automatically on save.

List { name, path, size } for every stored file, or delete one by name.

Opens a stored file in the system's default handler via a content URI (e.g. to preview a PDF you generated).

Total bytes used, or wipe your entire data directory.

UI

showDialog(title, description, confirmJS, confirmText)sync

Shows a native alert dialog. confirmJS (optional) is JS evaluated back into your page if the user taps confirm.

hideDialog() / showToast(message)sync

Dismiss the current dialog, or show a short native toast.

Adds a button to the plugin's top bar (up to 3 at once; names must be unique). Tapping it evaluates jsCode back into your page. Omit imageUrl for a text button.

Evaluates arbitrary JS in your own page's context — mainly useful for host-driven UI (e.g. a top-bar action) to call back into your app code.

raise(message)sync

Navigates to the host's built-in error/debug page, passing your message through. Intended for surfacing an unrecoverable plugin error clearly rather than showing a broken page.

06 Signing instructions

Every install and update is verified against a content hash of your package. Signing proves that hash came from you, and — once you use it — locks future updates to your key. The supported, canonical way to sign a .dpplugin is the official sign_plugin command-line tool.

The sign_plugin CLI

sign_plugin wraps every step below — hashing, keypair generation, signing, and verification — into one tool, so you never have to reproduce the root-hash algorithm by hand. It reads and writes .dpplugin files directly.

CommandDescription
sign_plugin genkey --out <name>Generates a new RSA-2048 keypair, writing <name>_private.pem and <name>_public.b64. Keep the private key offline — it's the only thing that can produce updates once a plugin is pinned to it.
sign_plugin sign <file> --key <private.pem> --email <email>Computes the package's root hash, signs it with the given private key, and writes META-INF/signature-v2.txt back into the package. --email is stored alongside the signature and should match your manifest's author.
sign_plugin sign <file> --test-signature --email <email>Signs with a throwaway, time-limited development key instead of one you supply — no --key needed. Meant for local testing only: the resulting install shows a visible expiry and is never key-pinned.
sign_plugin verify <file> --pubkey <public.b64>Recomputes the root hash and checks the package's embedded signature against the given public key, reporting ok, signature-invalid, or tampered.
sign_plugin manifest <file>Prints the parsed manifest.ini (and any per-locale variants) from inside the package, and flags missing required fields — a quick sanity check before signing.
bash
# 1. Generate your signing keypair (once — reuse it for every future update)
sign_plugin genkey --out mykey

# 2. Sign a package with your own permanent key
sign_plugin sign plugin.dpplugin --key mykey_private.pem --email email@users.darkpurpleof.github.io

# 2b. …or sign with a temporary key for local testing only
sign_plugin sign plugin.dpplugin --test-signature --email email@users.darkpurpleof.github.io

# 3. Verify a signed package against a public key
sign_plugin verify plugin.dpplugin --pubkey my_public_key.b64

# 4. Inspect the manifest packed inside a .dpplugin
sign_plugin manifest plugin.dpplugin
Download the signing tool Compatible with most OS platforms
Prefer to sign by hand?
Everything sign_plugin sign does is a thin wrapper around the root-hash algorithm and plain SHA256withRSA signing below — useful if you're scripting your own release pipeline.

How the integrity hash is computed

Before anything is signed, the installer builds a single "root hash" over your package contents. You'll need to reproduce this exactly if you're signing outside the app:

  1. Walk every file in your package except anything under META-INF/, anything under data/, and the runtime marker files listed in §02.
  2. For each remaining file, compute SHA-256(fileBytes) as a lowercase hex string.
  3. Build one line per file as relativePath<TAB>hashHex, using forward slashes, then sort all lines lexicographically by path and join with \n.
  4. Take SHA-256 of that whole joined string (UTF-8) — its lowercase hex encoding is the root hash.
pseudocode
entries = [ (path, sha256hex(read(path))) for path in package if not excluded(path) ]
entries.sort(by=path)
manifest = "\n".join(f"{path}\t{hash}" for path,hash in entries) + "\n"
rootHash = sha256hex(manifest.encode("utf-8"))

Two signature slots

FileEnforcementBehavior
signature-v1.txtInformationalNever blocks an install or update on its own. Carries per-file hashes and an optional author email — useful as a provenance record.
signature-v2.txtEnforcedIf present, it must cryptographically verify or the install/update is rejected outright — for both fresh installs and updates, regardless of who's signed in. The first time a plugin is installed carrying a v2 signature, its public key is permanently pinned on that device: every future update must be signed by that exact same private key, with no bypass, warning-through, or re-auth escape hatch. A key change is treated the same way Android treats a changed APK signing certificate — as a different app.

Both files use the same plain-text field format:

META-INF/signature-v2.txt
version=v2
publicKey=MIIBIjANBgkqhkiG9w0BAQEFAAOCAQ8A...  # Base64, X.509 SubjectPublicKeyInfo (DER)
signature=Z3JlYXQgam9iIHJlYWRpbmcgdGhpcyBmYX...  # Base64, PKCS#1 v1.5
email=dev@example.com
The signature covers the root hash string, not the raw bytes
The bytes that get signed are the UTF-8 text of the root hash's hex string itself — not the concatenated file manifest, and not raw file contents. Sign exactly that string, or verification will fail.

Manual signing, step by step (advanced)

  1. Generate an RSA-2048 keypair. Keep the private key offline and never bundle it inside your .dpplugin.
    shell
    openssl genrsa -out private.pem 2048
  2. Export the public key in X.509/DER form and Base64-encode it — this is exactly what goes in publicKey=.
    shell
    openssl rsa -in private.pem -pubout -outform DER -out public.der
base64 -w0 public.der > public.b64
  3. Compute your package's root hash following the algorithm above (excluding META-INF/, data/, and the runtime marker files), and write it to a plain text file, e.g. roothash.txt, with no trailing newline.
  4. Sign that root-hash string with SHA-256 / RSA (PKCS#1 v1.5) — the same algorithm as Java's SHA256withRSA — and Base64-encode the signature.
    shell
    openssl dgst -sha256 -sign private.pem -out signature.bin roothash.txt
base64 -w0 signature.bin > signature.b64
  5. Write META-INF/signature-v2.txt with version=v2, your Base64 public key, your Base64 signature, and your email (recommended, matches your manifest's author for a consistent identity).
  6. Archive the package — manifest, icon, HTML/JS, and the completed META-INF/ folder together — as a .dpplugin file, and distribute it.
Unsigned and development-signed plugins
Shipping without META-INF/signature-v2.txt is allowed — updates simply aren't key-pinned. The host can also apply a temporary, ephemeral development signature of its own for local testing; those carry a visible expiry and are meant for pre-release iteration only, not distribution.

07 Install & update flow

What happens, in order, when a user opens your .dpplugin.

  1. Read the package. Every entry is read into memory except anything under data/, which is discarded unconditionally.
  2. Verify a v2 signature if present. An invalid v2 signature is a hard failure — this happens before anything else is checked, for both new installs and updates.
  3. Parse manifest.ini (locale-specific first) and require id, author, and version to be present.
  4. Check the app-version gate described in §03 against the first bracketed number in requires=.
  5. Reject overriding a built-in plugin. If a plugin with the same id ships bundled with the app itself, your package is refused — bundled plugins can't be replaced by an install.
  6. If this is an update (a plugin with this id is already installed): the installed plugin's pinned v2 public key, if any, must match the incoming package's key exactly, and the new version must not be numerically lower than the installed one.
  7. Extract the icon, downscaling to roughly 256×256 if larger, falling back to a default icon when none is packaged.
  8. Copy files into filesDir/plugins/<id>/, then write integrity metadata (root.sha256, files.sha256, and copies of any signature files you provided) into a fresh META-INF/.
  9. Mark the install source (store vs. external) so the host knows whether a "reinstall from store" option should be offered later.

Integrity & tamper checks

On every load, the host recomputes the root hash of the plugin's files on disk (same algorithm as §06, same exclusions) and compares it against the root.sha256 captured at install time. If a v2 signature is present, it's re-verified cryptographically against that fresh hash as well.

  • A mismatch, or a present-but-invalid signature, writes a corrupt.lock marker. The plugin then shows as Corrupted in the list and can't be opened until it's reinstalled.
  • If integrity now checks out again (e.g. after reinstall), any stale corrupt.lock is removed automatically.
  • Development-signed plugins carry an expiry; once past it, the plugin is treated as unavailable the same way a tampered one is.

You can query this yourself at runtime with PluginAPI.checkIntegrity(targetId, callback), which returns the full status object: rootHash, rootHashMatches, whether v1/v2 are present, whether each verifies, and an overall status of ok, unsigned, signature-invalid, or tampered.

08 Showing in Features

The Features carousel is a curated row on the home feed that surfaces a handful of installed plugins. Appearing there isn't automatic — it's driven entirely by manifest metadata and your plugin's integrity status.

Step-by-step: making your plugin eligible

  1. Install your plugin normally under filesDir/plugins/<your-id>/. Bundled (asset) plugins are never scanned for Features and won't appear here, even if their manifest otherwise qualifies.
  2. Add a feature= (or features=) key to manifest.ini whose value contains, case-insensitively, at least one of: utility, game, or management. Any other text in the value is ignored — it just needs to contain one of those words, so feature=game,puzzle works fine.
  3. Make sure your package is signed and passes verification (§07). Your integrity status must not be tampered or signature-invalid — an unsigned or informationally-signed (v1-only) plugin is still eligible, only a package that fails verification is excluded.
  4. Drop in an icon (icon.png) and at least one screenshot so the card isn't blank — see the two subsections below for the full set of slots you can fill.
  5. Reopen the home feed (or restart the app). The Features row re-scans plugins/ on every load, so there's no separate "submit" step — the moment your manifest qualifies and passes the integrity check, the card appears.
manifest.ini
id=weather-widget
name=Weather Widget
author=dev@example.com
version=1.0.0
description=Shows today's forecast on your feed.
tags=weather,widgets,forecast
feature=utility
preview=assets/preview.png
preview2=assets/preview-hourly.png
preview3=assets/preview-settings.png
screenshots=assets/shot-4.png,assets/shot-5.png,https://cdn.example.com/shot-6.png

Way more image slots — the screenshot gallery

A single preview= image is still all you need to appear in Features, but the card now supports a full gallery instead of one static image. Every slot below is optional and additive — list as many or as few as you like, in any combination:

SlotDescription
preview=Legacy single-image slot, treated as the first gallery image. Still fully supported for backward compatibility.
preview2= … preview20=Numbered slots for additional screenshots, shown in order after preview=. Twenty numbered slots are read out of the box — far more than the single image the card used to support.
screenshots=Comma-separated list of paths or URLs, appended after the numbered slots. There's no hard cap here — list as many screenshots as your plugin genuinely needs.
preview-<lang>=, preview-<lang>-1= … preview-<lang>-20=Locale-specific versions of the slots above (see Localization below) — these take priority over the generic slots when the device language matches <lang>.

Every entry is resolved the same way a classic preview= always was: an http://, https://, or file:// value is used as-is; anything else is treated as a path relative to your plugin's own folder and must exist on disk, or it's silently dropped rather than breaking the card.

Localized name, description & images

The Features card now follows the same per-device-locale resolution described in §03 instead of always reading the un-suffixed files:

  • manifest-<lang>.ini is read instead of manifest.ini whenever it exists for the current device language — so a Russian device sees the name, description, and tags from manifest-ru.ini automatically.
  • icon-<lang>.png is preferred over icon.png the same way, with icon.png as the fallback.
  • Screenshots follow the same rule via the preview-<lang>… slots above — ship a translated screenshot of your settings screen and it'll surface automatically for that locale, no code changes needed on your end.
  • If no localized file exists for the device's language, the un-suffixed manifest.ini / icon.png / preview… values are used, so you only need to localize what you actually want translated.

What's shown on the card

The author lookup happens on every scan
Display name and verified-badge status are fetched fresh each time the Features row loads — an author= value that isn't a real registered account simply falls back to showing the raw string, it won't fail the plugin out of the list.

09 Enable, disable & uninstall

Plugin state is tracked with two marker files, not a single flag — enabled.lock and disabled.lock, written directly into the plugin's own folder.

  • Enabling checks every declared dependency first (§03); if any fails, the toggle is refused and the user sees exactly which dependency and why.
  • Disabling a plugin that other enabled plugins currently depend on prompts for confirmation, listing every plugin that would be affected, before proceeding.
  • A plugin that declares lacks=turnonable ignores toggle requests entirely — it's always on.
  • Bundled (asset) plugins are always considered enabled and can't be toggled or uninstalled by the user.

Distribution sources

Each installed plugin remembers how it got onto the device, in installationSource.dat:

SourceMeaning
storeInstalled through the in-app plugin store. Eligible for one-tap "reinstall from store" if it's later removed, and for the host's own update-check/download flow.
externalInstalled by opening a .dpplugin from outside the app (file manager, browser download, link share). Updates must be delivered the same way — the host won't fetch these automatically.
bundledShipped inside the app itself as an asset. Always enabled, can't be updated, removed, or overridden by an installed package with the same id.
